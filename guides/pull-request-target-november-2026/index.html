pull_request_target
before November 2.

GitHub is moving an eligible set of public repositories from evaluation to enforcement of a default policy blocking pull_request_target on November 2, 2026. This does not mean every repository or every PR workflow will be disabled. Use the policy insights to check whether yours is affected before editing anything.

4 USDC: review one public YAML ↗Official GitHub guide ↗

Eligibility matters: the default applies to public repositories without an already-applicable Actions event policy. It does not apply to private or internal repositories and does not replace an existing applicable policy. The affected default was in evaluate mode before planned enforcement. Check current GitHub policy settings and Insights first; GitHub can update rollout details.

01 / Check the facts

Four checks before
changing CI.

This checklist is informational, not a claim that your repository is broken or compromised.

1 / INVENTORY

Find affected workflows

Search your own .github/workflows/*.yml and *.yaml for pull_request_target. Record trigger, token permissions, used environments and secrets. Do not upload credentials.

2 / INSIGHTS

Check policy evaluation

With appropriate repository administrator access, inspect Actions execution policy Insights. Identify runs GitHub says the default rule would block. A repository with an existing applicable policy may behave differently.

3 / TRUST

Separate privileged and untrusted code

Flag jobs with repository secrets, write tokens, untrusted fork checkout, untrusted script execution or dependency installation. pull_request_target runs in the base-repository trust context.

4 / DECIDE

Migrate, restrict, or allow

If high trust is unnecessary, consider pull_request with the least privilege. If genuinely necessary, write an explicit, narrowly targeted Actions event policy and ensure the privileged workflow never executes untrusted PR code.

02 / A minimal alternative

Safer default
for ordinary tests.

Illustrative workflow for an already configured Node.js project. Review each action and dependency before using it in your repository.

● ● ●   .github/workflows/pr-tests.yml — informational example
name: PR checks
on:
  pull_request:
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npm ci
      - run: npm test

This is not a drop-in migration for privileged automation. A fork PR run may require explicit approval, lacks normal secret access, and may have narrower token permissions. For production workflows, prefer independently reviewed full action commit SHAs and project-specific threat modeling; never move secrets to an untrusted pull_request job just to make tests pass.

Additional checkout protection already changed in June/July 2026: GitHub updated supported actions/checkout versions to refuse common fork-head checkout patterns in pull_request_target and some workflow_run contexts. This protection does not catch every unsafe shell/git download, alternate untrusted repository or event. Do not disable the protection merely to bypass a failing job.
